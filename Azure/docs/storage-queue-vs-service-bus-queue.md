# Azure Storage Queue vs Azure Service Bus Queue

Azure には2種類のキューイングサービスがある。両者の「できること・できないこと」を比較し、技術選定の判断材料とする。

参考: [Storage queues and Service Bus queues - compared and contrasted (Microsoft Learn)](https://learn.microsoft.com/azure/service-bus-messaging/service-bus-azure-and-service-bus-queues-compared-contrasted)

## 概要

- **Storage Queue**: Azure Storage インフラの一部。HTTP/HTTPS 経由の認証付き呼び出しで、シンプルな FIFO ライクなワークキューとして大量メッセージを安価に捌く用途。ストレージアカウントの容量上限まで数百万件規模のメッセージを保持できる。
- **Service Bus Queue**: より広範な Azure Messaging インフラの一部で、キューイングに加えて Pub/Sub やより高度な統合パターンをサポートする。複数プロトコル・データ契約・信頼境界・ネットワーク環境をまたぐアプリケーション統合を想定して設計されている。

## 容量・上限

| 比較項目 | Storage Queue | Service Bus Queue |
| --- | --- | --- |
| 最大キューサイズ | 5 PiB(ストレージアカウント単位の容量に制限) | 1 GB〜80 GB(Standard/Premium、パーティション有効時) |
| 最大メッセージサイズ | 64 KB(Base64エンコード時は実質48KB)。Blobと組み合わせれば1件あたり最大200GBまで拡張可能 | 256 KB / 1 MB / 100 MB(ヘッダー込み、ヘッダー最大64KB。サービス層に依存) |
| 最大メッセージTTL | 無期限(api-version 2017-07-27以降) | TimeSpan.MaxValue |
| 最大キュー数 | 無制限 | Standard: 10,000 / Premium: 1,000 per Messaging Unit(namespace単位) |
| 最大同時接続クライアント数 | 無制限 | 5,000 |

**できること・できないこと**: 大量メッセージ・大容量キューが必要なら Storage Queue、1メッセージが大きい(256KB超)場合は Service Bus Queue(Premium)が有利。逆に Service Bus はキューサイズ自体に上限(最大80GB)があるため、80GB超のバックログを溜める用途には向かない。

## 基本機能(Foundational capabilities)

| 比較項目 | Storage Queue | Service Bus Queue |
| --- | --- | --- |
| 順序保証(FIFO) | **できない**(可視性タイムアウト失効時に順序が崩れうる) | **できる**(メッセージセッションを使用時のみ) |
| 配信保証 | At-Least-Once | At-Least-Once(Peek & Lock、既定) / At-Most-Once(Receive & Delete) |
| アトミック操作(トランザクション) | **できない** | **できる**(単一キュー内のローカルトランザクション) |
| 受信方式 | ノンブロッキング(即時応答) | ブロッキング(ロングポーリング、最大24日) / ノンブロッキング(.NET管理APIのみ) |
| Push型API | **できない** | **できる**(.NET, Java, JavaScript, Go SDK) |
| 受信モード | Peek & Lease | Peek & Lock / Receive & Delete |
| 排他制御 | リース(Lease)ベース | ロック(Lock)ベース |
| リース/ロック期間 | 既定30秒、最大7日(メッセージ単位で更新可) | 既定30秒(キュー単位。手動または自動ロック更新が可能) |
| リース/ロックの粒度 | メッセージ単位 | キュー単位(全メッセージ共通、更新は可能) |
| バッチ受信 | **できる**(最大32件を明示指定) | **できる**(プリフェッチまたはトランザクション経由) |
| バッチ送信 | **できない** | **できる**(トランザクションまたはクライアント側バッチング) |

> **補足: 「アトミック操作(トランザクション)」の対象範囲**
> ここで言うトランザクションは **同一キュー内でのメッセージ操作同士**(例: あるメッセージをCompleteしつつ、別の新規メッセージを同じキューに送信する、を1単位でコミット/ロールバックする)を指す「ローカルトランザクション」であり、外部のRDBやBlobなど**別の永続化ストアとの分散トランザクション(2相コミット的な連携)はサポート対象外**。DB書き込みとメッセージ送信を両方確実に行いたい場合は、Outboxパターンなどをアプリ側で別途実装する必要がある。Storage Queueにはこの「キュー内ローカルトランザクション」自体が存在しない。

## 高度な機能(Advanced capabilities)

| 比較項目 | Storage Queue | Service Bus Queue |
| --- | --- | --- |
| スケジュール配信 | できる | できる |
| 自動デッドレター | **できない**(DequeueCountを見て自前実装が必要) | **できる**(TTL失効や処理失敗時に `$DeadLetterQueue` へ自動移動) |
| キューTTLの後から延長 | できる(可視性タイムアウトの更新) | できる(専用API) |
| ポイズンメッセージ対策 | できる(DequeueCountを監視して自前で判定) | できる(自動デッドレター) |
| サーバーサイド トランザクションログ | **できる** | **できない** |
| ストレージメトリクス | できる(分単位のリアルタイムメトリクス) | できる(メッセージメトリクス) |
| 状態管理(Active/Disabled等) | **できない** | **できる** |
| メッセージの自動転送(Autoforward) | **できない** | **できる**(多数のキューを1つに集約可能) |
| キューのパージ | できる | できる |
| メッセージグループ(セッション) | **できない** | **できる**(メッセージセッション) |
| メッセージグループ単位のアプリケーション状態保持 | **できない** | **できる**(セッション状態) |
| 重複検出 | **できない** | **できる**(送信側で設定可能、メッセージID基準) |
| メッセージグループのブラウズ | **できない** | **できる** |
| セッションIDによるフェッチ | **できない** | **できる** |
| メッセージ内容の更新 | **できる**(進捗チェックポイント保存に利用可) | セッション状態経由で同等機能を実現可能 |

## 管理・運用機能

| 比較項目 | Storage Queue | Service Bus Queue |
| --- | --- | --- |
| 管理プロトコル | REST over HTTP/HTTPS | REST over HTTPS |
| 実行時プロトコル | REST over HTTP/HTTPS | REST over HTTPS / AMQP 1.0(TCP + TLS) |
| 主要言語SDK | .NET, C++, Java, PHP, Node.js | .NET, C++, Java, PHP, Node.js |
| 任意メタデータの付与 | **できる**(name/valueペア) | **できない** |
| キュー名の制約 | 3〜63文字、小文字英数字・ハイフンのみ | 最大260文字、大文字小文字区別なし、`.` `_` も可 |
| キュー長の取得 | できる(近似値。TTL失効分の誤差あり) | できる(正確な値) |
| Peek(ロックせず覗き見) | できる | できる |

## 技術選定の判断基準

### Storage Queue を選ぶべきケース

- 80GBを超える規模のメッセージをキューに溜める必要がある
- メッセージ処理の進捗をメッセージ自体に保存し、クラッシュ後に途中から再開したい
- キューに対する全トランザクションのサーバーサイドログが必要
- ストレージ(Blob/Table)と統一的なプログラミングモデルで運用したい
- 大量・低コストのシンプルなバックログ処理(疎結合化、負荷平準化)が目的

### Service Bus Queue を選ぶべきケース

- ポーリング不要な受信(ロングポーリング)が必要
- 厳密なFIFO順序保証が必要(メッセージセッション使用)
- 自動重複検出が必要
- セッションIDによる並列ロングランニングストリーム処理をしたい
- 複数メッセージの送受信にトランザクション(アトミック性)が必要
- メッセージサイズが64KBを超え、256KB〜1MB(Premiumなら最大100MB)程度になりうる
- センダー/レシーバーごとに異なる権限を与えるロールベースアクセス制御が必要(Managed Identity認証等)
- AMQP 1.0 標準プロトコルを使いたい
- 将来的にキューからPub/Subパターンへの移行(Topics/Subscriptions)を見据えている
- At-Most-Once / At-Least-Once の配信保証を追加インフラなしで使い分けたい
- メッセージのバッチ発行・消費が必要
- 自動デッドレターやメッセージ状態管理(Active/Disabled等)による運用性が必要

## 実際のユースケース例

### Storage Queue

**向いている例**

- **画像/動画のサムネイル生成バックログ**: ユーザーが大量にファイルをアップロードするたびにキューへジョブを積み、Worker(Azure Functions等)がスケールアウトしながら消費する。順序は問わず、とにかく安く・大量に捌きたいケース。
- **バッチジョブのキューイング**: 数百万件規模のレコード処理(例: メール一括送信、CSVの行単位処理)を1メッセージ=1タスクとしてキューに積む。Storage Queueの5PiB/無制限キュー数という上限の緩さが活きる。
- **進捗のチェックポイント保存**: 長時間かかる処理で、Workerがクラッシュしても再開できるよう、メッセージ内容自体に処理途中の状態を書き戻しながら進める(UpdateMessage)ケース。
- **既存のBlob/Tableと合わせた運用**: すでにStorageアカウントを使っており、同じ管理系(監視・課金・SDK)で完結させたい小〜中規模システム。

**向いていない例**

- **注文処理や決済のような順序・整合性が重要な処理**: FIFO保証がなく、可視性タイムアウト失効で順序が崩れうるため、処理順序が結果に影響するケースには不向き。
- **重複を絶対に避けたい処理**(例: 同じ決済を二重実行してはいけない): 重複検出機能がなく、At-Least-Onceのみのため、アプリ側で冪等性を必ず作り込む必要がある。
- **DBへの書き込みとキュー送信を一緒に確定させたい処理**: ローカルトランザクションが存在しないため、Outboxパターン等を自前実装しないと不整合が起きうる。
- **1メッセージが64KBを超えるペイロードを頻繁に扱う処理**: Blob併用の回避策はあるが、素直にService Busの方が適する。

### Service Bus Queue

**向いている例**

- **注文処理・決済ワークフロー**: メッセージセッションによるFIFO保証や、複数操作(在庫引当メッセージのCompleteと請求メッセージの送信など)をローカルトランザクションでまとめて確定させたいケース。
- **金融・請求など重複実行が致命的な処理**: 送信側の重複検出により、ネットワーク再送等で同じメッセージが二重処理されるのを防げる。
- **マイクロサービス間の疎結合な非同期連携**: AMQP 1.0や.NET/Java等のPush型APIで、ポーリングせず即座にメッセージを受け取りたいケース。
- **処理失敗メッセージの自動隔離が必要な運用**: 自動デッドレター($DeadLetterQueue)により、失敗メッセージの調査・再処理フローを自前実装せずに済む。
- **将来Pub/Subへ拡張しうる設計**: 最初はQueueで始め、後からTopics/Subscriptionsへの移行(複数コンシューマーへの配信)を見据えている場合。
- **IoTデバイスやパートナー企業からのメッセージを、送信者ごとに異なる権限で受け付けたい**: Managed Identity/RBACによる送受信者別のアクセス制御が必要なケース。

**向いていない例**

- **数百GB〜PB級の大量バックログを溜め込む処理**: キューサイズの上限が最大80GB(パーティション有効時)のため、Storage Queueのような超大容量の滞留には不向き。
- **とにかく低コストで単純なジョブキューを大量に捌きたいだけの処理**: Service Busは機能が豊富な分、単純なワークキュー用途にはオーバースペック・コスト高になりがち。
- **1メッセージが100MBを大きく超えるような巨大ペイロード**: Premium層でも上限があるため、大容量データはBlob Storageに置いて参照(URL)だけをメッセージに載せる設計が必要。
- **サーバーサイドの全トランザクションログを監査要件として必要とする処理**: Service Bus側にはStorage Queueのようなサーバーサイド全操作ログ機能がない。

## まとめ

| 観点 | 有利な方 |
| --- | --- |
| 大容量・低コストの単純キュー | Storage Queue |
| 大きいメッセージサイズ | Service Bus Queue |
| FIFO順序保証 | Service Bus Queue |
| トランザクション・アトミック操作 | Service Bus Queue |
| 自動デッドレター/重複検出 | Service Bus Queue |
| サーバーサイドの全操作ログ | Storage Queue |
| Pub/Subへの発展性 | Service Bus Queue |
| プロトコルの柔軟性(AMQP) | Service Bus Queue |

両者は排他的ではなく、要件によっては用途ごとに使い分ける(あるいは併用する)のが公式ドキュメントの推奨スタンスである。
