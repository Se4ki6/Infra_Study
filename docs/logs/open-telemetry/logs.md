## [ログ | OpenTelemetry](https://opentelemetry.io/ja/docs/concepts/signals/logs/)

---

### ログ

- ログはイベントを記録する、タイムスタンプ付きのテキストレコード
  - 任意のメタデータを含められる
  - 構造化ログが推奨される
  - 多くの言語に組み込み機能や広く使われているログライブラリがあり、他のテレメトリーシグナルより長い歴史を持つ

### OpenTelemetry のログ

- OpenTelemetry はログレコードを生成する Logs API と SDK を提供する
  - API はアプリケーションから直接使える
  - 既存のロギングライブラリやブリッジ経由でも使える
- ログはロギングプロバイダーを通じて送られるデータ全般で、イベントはログの特殊な種類
  - すべてのイベントはログだが、すべてのログがイベントとは限らない
- OpenTelemetry は既に生成されたログも扱う
  - 他のシグナルとの関連付けやコンテキスト属性の追加ができる
  - 異なるソースのログを共通形式に正規化し、処理・エクスポートできる

#### OpenTelemetry コレクター

- Collector はログ収集・処理のためのツールを提供する
  - 特定のログソースを解析するレシーバー
  - `filelogreceiver` は任意のファイルを読み込み、形式や正規表現に基づいて解析できる
  - `transformprocessor` などのプロセッサーはネストされたデータの解析、フラット化、値の追加・削除・更新を行える
  - OpenTelemetry 以外の形式に出力するエクスポーターもある
- OpenTelemetry 導入の最初の段階として、Collector を汎用ログエージェントとしてデプロイすることがある

#### アプリケーション

- OpenTelemetry のログは、任意のログライブラリまたは言語組み込みのログ機能から作成できる
- 自動計装や SDK を利用すると、既存ログをアクティブなトレースやスパンに自動関連付けし、その ID をログ本文に含められる

#### 言語サポート

- Logs は OpenTelemetry 仕様上 Stable のシグナル
- ページに記載された各言語実装のステータス
  - Stable: C++、C#/.NET、Java、PHP
  - Release candidate: Go
  - Beta: Rust
  - Development: Erlang/Elixir、JavaScript、Python、Ruby、Swift

### 構造化、非構造化、半構造化ログ

- OpenTelemetry は様々なログ形式を扱えるが、分析のしやすさは形式によって異なる
- JSON であることだけでは構造化ログとは言えない
  - 構造化ログには、安定したスキーマ（フィールド名・型・意味）が必要

#### 構造化ログ

- 構造化ログは定義済みで一貫したスキーマまたは型付きフィールドを持つ
  - JSON、Protocol Buffers（protobuf）など、テキスト表現の形式は問わない
  - 下流システムが確実に解析・解釈でき、検証、トレースやメトリクスとの関連付け、大規模分析に適する
- インフラでは Common Log Format（CLF）がよく使われる
- CLF と末尾の JSON ブロックを組み合わせたハイブリッド形式や拡張形式もある
  - 必要な箇所を解析・抽出して正規化すると、後続ツールで一貫して分析できる
  - Collector の `filelogreceiver` はログ解析の標準化に使える

#### 非構造化ログ

- 非構造化ログは一貫した構造を持たず、人間には読みやすいことが多い
- 開発ではよく使われるが、本番環境のオブザーバビリティでは推奨されない
  - 大規模な分析には解析・前処理が必要になりやすい
  - タイムスタンプや本文の抽出に正規表現や個別パーサーが必要になる例がある
  - 標準ログフレームワークで構造化ログに切り替える方が作業量を抑えられる場合がある

#### 半構造化ログ

- 半構造化ログは一定のパターンがあり機械で読み取りやすいが、システム間で形式や区切り文字が統一されていない
  - キーと値のペア形式や、メッセージごとにフィールド名・型が異なる JSON などが該当する
  - 非構造化ログより解析しやすいことが多い
  - 分析前にマッピングや型変換などの正規化が必要な場合がある

### ロギングが有効かどうかの確認

- 通常、ログ呼び出しの前に `logger.Enabled` を確認する必要はない
  - 無効なロガーに対する Logs API の呼び出しオーバーヘッドは最小限
  - 毎回確認するとパフォーマンスを下げ、コードを複雑にする
- ログ呼び出しの引数評価が高コストで、そのコストを避けたい場合は `Enabled` が役立つ
  - 例: ログ属性をデータベースから取得する、または高コストな計算で作る
- ガード内の処理は副作用のないものにする
  - ロギングが有効なときだけ実行されるため、他の処理が依存するとログ設定によって動作が変わる
- `Enabled` の結果は設定変更で変わり得るため、ログレコードごとに評価し、キャッシュしない

### OpenTelemetry ログコンポーネント

#### ログアペンダー／ブリッジ

- ログアペンダー／ブリッジは既存のロギングライブラリを OpenTelemetry に接続する
- アプリケーション開発者は Log Bridge API を直接呼ばず、利用するログライブラリを OpenTelemetry のログエクスポーターへ出力するよう設定する
- 言語 SDK がこの機能を提供する

#### ロガープロバイダー

- `LoggerProvider` はロガーを作成するファクトリー
- 通常は一度初期化され、アプリケーションと同じライフサイクルを持つ
  - 初期化にはリソースとエクスポーターの初期化も含まれる
- Logs Bridge API の一部であり、主にロギングライブラリ作者向け

#### ロガー

- ロガーはロガープロバイダーから作られ、ログレコードを作成する
- Logs Bridge API の一部であり、主にロギングライブラリ作者向け

#### ログレコードエクスポーター

- ログレコードをコンシューマーへ送る
  - 標準出力、OpenTelemetry Collector、オープンソースまたはベンダーのバックエンドなどが宛先となる

#### ログレコード

- ログレコードはイベントの記録を表し、特定の意味を持つトップレベルフィールドと、任意の値・型を持つリソース／属性フィールドからなる
- 主なトップレベルフィールド
  - `Timestamp`: イベント発生時刻
  - `ObservedTimestamp`: イベントが観測された時刻
  - `TraceId`、`SpanId`: リクエストのトレース ID、スパン ID
  - `TraceFlags`: W3C トレースフラグ
  - `SeverityText`、`SeverityNumber`: 重要度のテキスト表現（ログレベル）と数値表現
  - `Body`: ログレコード本文
  - `Resource`: ログの発生元
  - `InstrumentationScope`: ログを出力した計装スコープ
  - `Attributes`: イベントに関する追加情報
  - `EventName`: イベントのクラスまたは種類を識別する名前
