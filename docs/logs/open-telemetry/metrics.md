## [メトリクス](https://opentelemetry.io/ja/docs/concepts/signals/metrics/)

---

### メトリクスとは

- メトリクスは、実行時に取得されるサービスの測定値。
  - 測定値を取得した時点のイベントをメトリクスイベントと呼び、測定値、取得時刻、関連メタデータで構成される。
- アプリケーションやリクエストのメトリクスは、可用性とパフォーマンスを把握する指標になる。
- カスタムメトリクスから、可用性がユーザー体験やビジネスへ与える影響を調べられる。
- 収集データは、障害のアラートや需要増加時の自動スケールなどにも利用できる。

### メータープロバイダー

- メータープロバイダー（`MeterProvider`）は `Meter` を作るファクトリー。
- 多くのアプリケーションでは一度だけ初期化され、アプリケーションと同じライフサイクルを持つ。
  - 初期化にはリソースとエクスポーターの初期化も含まれる。
  - OpenTelemetry で計測を始める際の通常の最初のステップ。
- 一部の言語 SDK では、グローバルなメータープロバイダーがすでに初期化されている。

### メーター

- メーターはメータープロバイダーから作成され、メトリクス計装を作って実行時の測定値を取得する。

### メトリクスエクスポーター

- メトリクスエクスポーターは、メトリクスデータをコンシューマーへ送る。
  - 開発時のデバッグ用標準出力、OpenTelemetry Collector、オープンソースまたはベンダーのバックエンドなどが送信先になる。

### メトリクス計装

- メトリクス計装は、名前、種類、任意の単位、任意の説明で定義される。
  - 名前・単位・説明は開発者が定義できる。
  - リクエストやプロセスのような一般的な計装では、セマンティック規約で定義される場合もある。
- 計装の種類:
  - Counter（カウンター）: 時間とともに増加して蓄積する値。車のオドメーターに相当する。
  - Asynchronous Counter（非同期カウンター）: カウンターと同じ性質だが、エクスポートごとに一度だけ値を取得する。連続した増分ではなく、集約値しか取得できない場合に使う。
  - UpDownCounter（アップダウンカウンター）: 増加も減少もする累積値。例: キュー内の作業項目数。
  - Asynchronous UpDownCounter（非同期アップダウンカウンター）: エクスポートごとに一度だけ値を取得する。例: 現在のキューサイズしか取得できない場合。
  - Gauge（ゲージ）: 読み取り時点の現在値を測る同期計装。車の燃料計に相当する。
  - Asynchronous Gauge（非同期ゲージ）: エクスポートごとに一度だけ現在値を取得する。
  - Histogram（ヒストグラム）: リクエストレイテンシーなどの値をクライアント側で集約する。値の分布を知りたい場合に向く。
    - 例: 1秒未満で完了したリクエストが何件あるか。

### 集約（アグリゲーション）

- 集約は、多数の測定値を組み合わせ、ある時間ウィンドウ内のメトリクスイベントについて統計値または推定統計値を作る手法。
- OTLP は集約済みのメトリクスを伝送する。
- OpenTelemetry API は各計装のデフォルト集約を提供し、ビューで変更できる。
- トレースがリクエストのライフサイクルと個々の処理の文脈を記録するのに対し、メトリクスは集約統計を提供する。
- メトリクスの利用例:
  - プロトコル別にサービスが読み取った総バイト数や、リクエストごとのバイト数を報告する。
  - システムコールの継続時間、リクエストサイズの傾向を把握する。
  - プロセスの CPU・メモリ使用量、口座の平均残高、現在処理中のリクエスト数を報告する。

### ビュー

- ビューは SDK が出力するメトリクスをカスタマイズする仕組み。
  - 処理する計装や無視する計装を選べる。
  - 集約方法や、メトリクスに出力する属性も変更できる。

### カーディナリティ制限

- メトリクスのカーディナリティは、そのメトリクスで報告される属性のユニークな組み合わせ数。
- SDK は組み合わせごとにデータポイントの集約状態をメモリに保持するため、カーディナリティがメモリコストに影響する。
  - リクエスト数ではなく、ユニークな属性の組み合わせ数に応じてメモリ使用量が増える。
  - ユーザー ID や生の URL パスなどの高カーディナリティ属性は、メモリ使用量を際限なく増やすおそれがある。
- OpenTelemetry メトリクス SDK は、メトリクスストリームごとに追跡する組み合わせ数を制限する。
  - デフォルトの上限は 2000 で、ビューから変更できる。
- 上限を超えた測定値は破棄されず、属性 `otel.metric.overflow=true` を持つ単一のオーバーフローデータポイントに集約される。
  - 測定値は保たれ、全体の合計は正確なまま。
  - SDK は設定数を超える組み合わせを追跡しないため、メモリ使用量が制限される。
  - 共通の属性マーカーにより、サービス・言語・バックエンドをまたいでオーバーフローを検出できる。
- オーバーフローした測定値では属性が失われるため、属性でフィルターまたはグループ化したクエリは過少に数える場合がある。
  - 例: `url.path` と `success` を記録するカウンターがオーバーフローすると、両属性とも失われる。`success=false` だけでエラー率を集計するクエリも測定値を見逃し得る。
- 制限の対象は、メトリクス API で測定値を記録する際に指定する属性。
  - `service.name` や `service.instance.id` などのリソース属性、メーター作成時に設定する計装スコープ属性には適用されない。
  - これらの属性はオーバーフロー中もデータポイントに記録され、クエリ可能。
  - 制限回避のために測定属性をリソースへ移すのではなく、属性が表す対象に応じて配置する。リソースはテレメトリー生成元、計装スコープは計装ライブラリ、測定属性は個々の測定を記述する。
- 同期計装では集約テンポラリティにより、SDK が集約状態を回収する頻度、ひいては上限に達する速さが変わる。
  - Delta（デルタ）: 各サイクル後に状態をリセットするため、1サイクル内の組み合わせが制限対象。
  - Cumulative（累積）: サイクルをまたいで状態を保持するため、上限到達後はプロセス再起動まで新しい組み合わせがオーバーフローする。
  - 非同期計装には別のルールがある（ページでは詳細説明の対象外）。
