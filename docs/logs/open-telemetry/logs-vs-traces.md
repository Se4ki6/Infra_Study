## [Logs and Traces | OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/)

---

### まず一言で

- ログ（Logs）は「ある時点で何が起きたか」を記録するイベントの記録。
- トレース（Traces）は「一つのリクエストがシステムをどう通り、各処理にどれだけかかったか」を表す。
- 同じ出来事を別の角度から見るシグナルなので、どちらか一方で置き換えるものではない。

### 例（補足）: 商品購入リクエスト

- ブラウザーから注文サービスへリクエストが届き、注文サービスが在庫サービスとデータベースを呼び出す。
- トレースでは、この一連の処理を一つの `trace_id` で関連付ける。
  - ルートスパン: `POST /orders` の処理全体
  - 子スパン: 在庫確認、データベース書き込みなど個々の処理
  - 各スパンの開始・終了時刻から、どの処理が遅いかを見つけられる。
- ログでは、各時点の具体的な出来事を記録する。
  - 例: `在庫確認を開始`、`在庫不足: item_id=...`、`注文を保存`
  - エラーの詳細や業務上の値など、トレースのスパンだけでは分からない内容を残せる。
- ログに `trace_id` と `span_id` を付けると、該当リクエストのトレースや処理箇所へ移動しやすくなる。

### 違い

| 観点 | ログ | トレース |
| --- | --- | --- |
| 記録の単位 | 個々のイベントやメッセージ | リクエストなどの処理と、その中の作業単位（スパン） |
| 時間の表し方 | 主にイベントが起きた時刻 | スパンの開始・終了時刻と親子関係 |
| 得意な問い | 「その時、何が起きたか」「どんな値やエラーだったか」 | 「どの経路を通ったか」「どこで時間がかかったか」 |
| 形 | 単独のレコードとしても役立つ | `trace_id` とスパン間の関係で一連の処理を組み立てる |

### ログを使う場面

- エラーの内容、入力値、状態変化など、個別の出来事の詳細を調べる。
- 人が読めるメッセージや、検索・集計しやすい構造化フィールドを残す。
- リクエスト以外の出来事（定期バッチ、起動、設定変更など）も記録する。
- ログ単体でも発生時刻や発生元を手掛かりに調査できる。ただし、分散システムの複数サービスにまたがる処理をログだけで追うのは難しい場合がある。

### トレースを使う場面

- サービスをまたぐリクエストの経路や、処理の親子関係を調べる。
- 全体の所要時間を各スパンに分け、遅延の原因となる呼び出しを探す。
- 失敗したリクエストがどのサービスや操作で失敗したかをたどる。
- トレースにはリクエスト中のあらゆる詳細が自動で入るわけではない。必要に応じてスパン属性、スパンイベント、ログを使い分ける。

### 一緒に使う

- トレースは処理の流れと所要時間を示し、ログはその流れの中で起きた出来事の詳細を補う。
- OpenTelemetry のログレコードには `TraceId` と `SpanId` を含められる。これらを付けると、ログとトレースを実行コンテキストで相関できる。
- 相関には時刻や発生元も役立つが、`TraceId` / `SpanId` による関連付けは、同じリクエストのログやスパンを直接結び付ける手掛かりになる。
- 既存のログを使う場合、OpenTelemetry の SDK や自動計装、ログブリッジなどでアクティブなトレースとの関連付けが可能。ただし、利用環境や計装方法に依存する。

### 調査の進め方の例（補足）

- 「注文 API が遅い」なら、まずトレースで時間のかかったスパンを探す。
- 「在庫サービスが失敗している」なら、該当スパンのエラー状態を確認し、関連付いたログからエラー内容や対象データを調べる。
- ログにトレース ID がない場合は、時刻やサービス名などで候補を絞れるが、同時に処理されたリクエストが多いと特定しにくい。

### 覚え方

- ログ: 出来事の記録。
- トレース: リクエストの道筋と各処理にかかった時間。
- ログにトレースコンテキストを付けると、道筋の中の出来事を詳しく調べられる。
